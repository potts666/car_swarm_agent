# rolling_interval_001：跨完整服务与换权的逐拍局部MPC

日期：2026-11-15。依据mainline_checkpoint_2026-11-15_v12、LOCAL-FRAME-v1、CURVE-JOINT-v1及用户报告slack_release_001。

给Ubuntu Codex：新建rolling_interval_001，完成共同规则审查、最小实现、限定区间控制实验和独立验收。历史、原始失败、论文保留，Git提交由用户另行安排。先以任务逐项执行、核对，再进入后续阶段。

**目标：** 将“事件后连续两轮更新”推进为一段完整服务过程内的逐拍滚动计算，跨越停车调轮、恢复运动、弯道/曲率变化、制动停车、实际Clear、权限转让及后继启动。

**架构：** 四车均有本车OCP入口；每拍以实际联合源和封存预测重建本车模型及接收后续，各车独立求解，依当前真实合同分块认可。合法零输入/唯一输入阶段按共同证明处理；候选受拒则保留认可计划。释放观察器继续逐拍运行。

**技术：** 复用slack_release/local_frame/curve_joint的Python、Clarabel、实际ZOH/变分、量化与区间Audit。先列implementation_map及所有调用者，再修改共同入口；配置、worker、fixtures和独立裁判同步核对。

## 1. 本轮问题与实验规模

前一报告已完成三次真实释放、8次局部新求解、完整1615拍任务。本轮集中回答：

1. 接收域与实际后续能否逐拍生成、使用和移位，持续跨越完整服务？
2. 模式、输入自由度、弯道与停车守卫切换时，零锚点和可用优化方向如何变化？
3. 滚动修改累计后，Clear、资源租约及未来任务是否继续合法？
4. 哪些拍采用新数值候选、哪些拍沿备份、哪些拍可给出解析最优/唯一输入证明？

本轮只跑一条正式滚动数值主轨迹，解析参照零新增求解。区间最多512个控制拍，每拍最多4个本车worker，**正式尝试总上限2048次**。这是一项上限，实际数量由逐拍合法自由度决定；唯一输入/已证最优的拍跳过数值求解并给证书。异常尝试计入，所有释放前登记。

这一规模用于检查持续覆盖。先完成零调用预检与首个32拍阶段，再自动进入剩余区间；达到停止条件则保留已执行轨迹，交付明确分项结果。

## 3. 区间由事件定义，拍号作回归参考

目标服务车：初始有效请求排序中继首车之后的服务车，当前地图预期B1。按现有请求/owner关系识别，ID只用于配置和既有破同序。

**起点k_start：** 前驱首个有效Clear引发的内部owner提前事务成功后，目标车准备恢复服务的控制边界。保留该事务前完整策略与源，当前报告参照406。

**终点k_end：** 目标服务车完成实际Clear并认可下一次换权，随后下一服务车开始实际有效运动，再连续运行N=32拍后结束。记录所用守卫和每一时刻。当前报告目标车Clear参照786，后继启动/运动由实际状态确定。

区间长度最多512拍。每拍扫描事件和实际状态；到达512仍未满足终点时停止新增数值调用，沿当前已认可完整策略完成任务，分项报告覆盖情况。

R-anchor与R-rolling共享k_start以前的实际解析前缀。R-anchor在区间继续解析策略与相同释放规则；R-rolling在区间逐拍重建并优化，区间外继续认可完整后续。额外缩时按实际报告；当前研究重点为持续闭环覆盖。

## 4. 每拍共同计算规则

1. **实际源：** 读取各车pose/v/delta/history、旧输入尾段、接收链、当前权限/框架/期限；记录实际后继与上一首拍的绑定。
2. **事件：** 按同一逻辑边界顺序执行Clear观察、已认证改约及事务认可，再封存本轮模型上下文。事件改变模型时，旧组装作废，按新context重新生成。
3. **移位候选：** 由上一真实计划去首项、附加已认可后续，构造本轮零增量锚点；验证初态、模式/接收、终端与权限。
4. **本车自由度：** 从实际E/T、固定输入和物理活跃行计算可行方向与维数，生成阶段分类。每辆车都经过同一入口。
5. **数值：** 对需优化的各车生成本车64输入模型，封存邻车预测；独立worker组装/求解。保留原有范数辅助变量及缩放，实际维数如实记录。
6. **受理：** native状态、原行、精确量化、真实目标、连续车身/占用包含、Q/K、完整后续、模式、期限全部核对。固定线搜索复用同一raw。
7. **认可与执行：** 根据当前真实依赖块提交；各车执行本车合法编号的首拍。保存实际联合后继，再开始下一拍。

同一逻辑拍的各车共享封存版本。worker顺序或并发按实际实现记录；本轮物理推进保持共同逻辑节拍，计时单独报告。

## 5. 自由度与跳过求解的明确分类

每车每拍恰有一个主要分类：

- **numerical_update：** 存在合法优化自由度，实际调用求解器；受理/拒绝/采用分列。
- **unique_control：** 线性等式与阶段条件唯一确定允许输入或优化变量；保存秩、零空间及唯一解证书，直接执行已认可输入。
- **certified_optimum：** 当前J_E为非负二次型，零输入达到0且满足全套约束；或已有精确KKT/等价证书。直接保留计划。
- **fallback_after_failure：** 模型生成/求解/认证或认可失败，实际执行有效备份。失败根因单列。
- **goal_hold：** 已到目标并保留永久占用与零保持证书。

“当前速度为零”“单次优化变化很小”本身只作为状态信息；跳过求解需有上述证明。若终端后32拍仍含启动/转向自由度，应按实际模型判断。

保存所有车拍分类，单独统计：实际活动车、具有自由度的车、实际求解车及采用新输入的车。后续区间外模式也保留真实控制日志。

## 7. 连续更新需要额外核对的理论接口

本轮在rolling_theory.md逐项列明条件、公式与实际证书：

1. **接收继承：** 当前后继状态等于实际ZOH映射；移位计划包含于下一阶段实际OCP允许集合。阶段切换的集合包含与正半径条件明确。
2. **累积误差：** 每拍以实际源重新锚定，本轮输入/几何误差及保存尾段SE2包含分别计算；继承区间与新余项只计入对应来源。
3. **Q/K替换：** 新合同整体替换哪些旧义务、保留哪段后续，按实际phase和内容ID核对。新约生效前保留旧完整计划。
4. **持续可行与备份：** 逐拍OCP零锚点通过率及可行方向逐项统计；控制执行依靠当前有效合同。接收构造或行编码失败与native数值失败分别报告。
5. **释放与完成：** 更新后的真实尾段参与Clear；绝对期限非增，B逐拍与日历调整分列；SR-S/R/F条件保持。

所有“每拍都可解”的判断附本车模型/阶段/窗口范围及实际记录。连续滚动覆盖需以整个登记区间的逐拍清单核对。

## 8. 停止、修复与拒绝恢复

触发以下条件时停止新增数值释放，保存现场，沿已认可策略完成并独立审查：

- 有效备份、共同版本、初态衔接或物理安全检查失效；执行前先定位具体违规行/守卫。
- 连续3拍出现相同生成/受理根因，或累计调用达到2048、区间达到512拍。
- 自由度分类缺少证书，或下一阶段接收后续尚未建立。

若备份自身审查出现安全风险，保持仿真现场并报告首个反例，暂停实际输出至原因明确。源码修复保留原版本与已执行前缀；新版本从登记检查点分叉，所有新增尝试共用本轮总账，旧结果独立保留。每车每拍每版本最多一次native求解。

从主轨迹中选择两个真实检查点做零新增求解拒绝分支：

1. 模式切换/曲率边界附近损坏一个raw来源或K：本车回合法锚点，其余已认可相容输入继续。
2. Clear/换权附近缺一个相关ACK：整个受影响事务保留旧约，下一拍从真实新history重新评估释放；可用已保存合法候选或零增量，不伪装新求解。

两分支均执行完整后续至目标。回侵、端点重叠、接收phase错位、重复累计误差、外部私有hash误失效、已执行前缀修改作小型零调用回归。
