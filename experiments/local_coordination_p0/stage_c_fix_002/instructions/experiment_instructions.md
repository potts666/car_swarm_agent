# C0连续两轮实际重新优化验证任务

日期：2026-11-13。

**目标：** 在弯道、直线加速两个既有窗口，各连续两拍从实际状态重新优化，验证两份新候选的来源、受理、实际输出和后续接续。

**设计依据：** 随包`theory.md`第7节及C0_fix_001的完整证书受理。区域预约留在理论设计阶段。用户所说“先来后到”指研究先后顺序，车辆优先规则保持待设计。

**实现方式：** 在Ubuntu现有工程复用C0_fix_001，创建隔离的`stage_c_fix_002/`。按任务逐项实现与验证；无需新开分支或Git提交。

**技术条件：** Python、现有区间模型、Clarabel0.11.1及已有NumPy/SciPy；h=0.2s、N=32、64输入/65变量、rho=0.001、Q量化预留、居中等价锥、scale=1e-4、三个容差1e-10、max_iter=300、5s预算。受理规则`certificate_suboptimal_v1`保留完整物理与后续检查。

## 2. 先确认本次新增了什么

C0_fix_001每个接口只产生一次优化新候选；下一实际锚点重新生成了导数并验收旧尾段，随后继承执行。本任务要求下一锚点真正调用数值求解器，再验收和执行第二份新候选。

两个接口各运行一个受控分支：

```text
弯道：phase5新求解 → 受理并执行首拍 → phase6实际状态 → 新求解
直线：phase10新求解 → 受理并执行首拍 → phase11实际状态 → 新求解
```

第1轮也重新求解并保存本次来源。初始求解调用总数固定4次。两轮以后继续合法计划，完成既有239拍连接和下一车首拍，总计240拍。多车运动、资源预约、C2时长和大规模扫描暂存。

## 3. 改动范围与接口

| 位置 | 修改目的 |
|---|---|
| `fix_socp.py`或复用的求解入口 | 从本轮anchor/cert生成原行、组装、求解、量化及受理 |
| `execute_fix.py`的两轮调度 | 在实际后继上触发第2次求解，保存事件并执行被认可计划 |
| `validate_fix.py` | 按每次事件的内容ID核对来源，移除仅能查固定初始probe键的依赖 |
| `accept_fix.py` | 独立重建两轮实际状态与两份新计划，核对父子链和连续几何 |
| 最小自检与汇总 | 覆盖陈旧来源、第二轮失败续行、接收/K替换及新旧预算 |

复用已有函数`anchor_for`、`build`、`verify`、`rows_for`、`assembly`、`admit`、`A.validate_candidate`、`A.commit`、`A.shift`和`Replay`。先梳理这些调用关系，再做最小共享改动。

每轮求解事件至少绑定：run/interface/phase、实际history、parent_plan_id、anchor_id、derivative_id、assembly_id、raw_result_id、policy_result_id、accepted_plan_id及提交编号。原始数值结果与受理结果分别保存。受理失败仍保存原始对象及原因。

## 4. 任务一：在真实后继上重新求解

- [ ] 第1轮从当前实际状态创建anchor，重建32拍导数与原行，求解一次；完成完整认证和共同受理。
- [ ] 执行所选计划第一拍，以实际执行产生的五状态和history创建第2轮anchor。它的parent为上一轮共同受理并移位后的计划。
- [ ] 第2轮独立生成32拍导数、约束和组装对象，求解一次，再执行完整受理。新接收位置由本轮phase+32计算。
- [ ] 保存两次完整输入对象与数值输出，独立检查器逐事件查内容ID，避免读取固定的curve_centered或straight_acceleration_centered初始提案。

每次实际改变计划都必须通过全套原行、ZOH连续车身、权限、接收、K、后续与预算检查。来源损坏或检查失败时执行当前已认可的真实尾段，并明确计为拒绝续行。

## 5. 任务二：处理重叠窗口中的旧K

第2轮32拍窗口会与上轮K及其接收条件重叠。例如弯道phase5的接收/K位于37；phase6的新接收/K位于38。第2轮优化窗口包含原K时刻37。

分别记录：旧接收条件仍需保留，或由新联合计划整体替换。若整体替换，新前缀、接收/K和后续必须重新证明合法，四车共同提交后一起生效。若拒绝，保留原K及其绑定条件继续执行。

- [ ] 自检旧pending_reset在新方案受理后如何处理，验证全过程及后续接续。
- [ ] 自检新方案拒绝以后，旧pending_reset的phase、输入、版本与父计划仍有效。
- [ ] 自检提交原子性：权限与接收条件采用同一份认可组合，执行端按共同编号选择计划。

源域、接收域和预算对象均保持原始物理意义。若第2轮32拍问题失去可行内空间，保留具体失败行和实际状态作为结果，分析重叠窗口的结构原因。

## 7. 指标与通过条件

每接口报告：两轮各自求解状态、原始/对偶残差、gap、提案数、完整检查结果、共同受理数、真实首拍差异、改动范数、实际输出、预算、接收/K时刻、开销、道路与车对净空下界。

能量逐轮比较本轮新计划与本轮旧候选的同一32拍，两个相邻窗口分别列出。实际执行收益用同一实际时间区间重算，重叠预测窗口的收益避免重复累计。

| 检查层 | 通过要求 |
|---|---|
| 实际来源更新 | 两次真实求解来自连续两拍的实际状态，各有新内容绑定 |
| 连续重新优化受理 | 每接口两份数值新候选均共同受理，实际输出和计划变化据实报告 |
| 实际安全接续 | 两接口240拍、连续净空、移位、接收/K、停车换权与独立验收通过 |
| 拒绝续行 | 第2轮来源/方案损坏时仍执行已认可真实尾段，检查通过 |

若第2轮只获得零增量，记录“优化调用及受理通过、无新增输入改变”。若第2轮拒绝且安全继承通过，记录“连续提案通过流程、连续两次受理未通过”，给出失败层；优先解释该反例。

本轮原设置固定。发生失败时保留证据并停止扩大扫描范围；分析报告后再决定定点改动。
