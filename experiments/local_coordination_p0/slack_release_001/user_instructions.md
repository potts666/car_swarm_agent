# slack_release_001：实际清空触发的重复释放与局部协商

日期：2026-11-14。依据mainline_checkpoint_2026-11-14_v11、LOCAL-FRAME-v1及用户报告local_frame_001。

给Ubuntu Codex：在新目录slack_release_001完成共同规则推导、最小代码改动、规定预算内控制实验和独立验收。先核对真实工程与原始证据，保留历史、原始失败和论文；Git提交由用户另行安排。

**目标：** 将已验证的单次内部改约/余量外授，变成由实际状态触发、可在同一任务中重复运行的释放策略，使局部节省沿资源依赖传播，保持多车活动、安全接续及有限完成。

**架构：** 每拍从实际五状态与有效合同判断资源清空；本车提出有认证后续的提前释放，目录发现真实依赖，受影响端点认可新框架，随后按实际依赖拆分。每车独立MPC，失败保留有效旧策略。

**技术栈：** 复用现有Python、Clarabel、区间ZOH、框架/接收生成、量化、目录与独立Audit。实施按下文任务依次核对；先做小型失败检查，再修复共同入口。实际文件名和调用者列在implementation_map.md。

## 1. 实验要回答的问题

1. 释放时间能否由实际车身清空、后续分离和接收守卫共同计算？
2. 单趟任务能否自动发生至少两次不同的有效释放/改约，包含一次内部owner调整和一次外部租约转让？
3. 节省怎样沿等待/资源依赖传播，哪些车辆提前，哪些承诺保持？
4. 连续两轮本车数值更新之后，释放、换权、接收及实际后续是否仍相容？
5. 缺ACK、陈旧提案、接收不适配等情况发生时，旧计划怎样继续，并使后续事件仍可运行？

预期贡献为一条可持续执行的在线规则及其条件证明、实例证书和完整控制轨迹。当前地图事件数量与收益按实际结果记录。

## 3. 三臂：分别识别释放策略与局部MPC的作用

|臂|资源调整|新增数值求解|用途|
|---|---|---|---|
|R-fixed|保持同一初始合同及保留余量|0|固定时序参考|
|E-anchor|实际状态触发重复释放，用认证解析锚点|0|识别释放与日历传播的作用|
|E-MPC|相同事件/提案规则，结合本车MPC|最多8次|验证释放与实际数值更新的组合|

三臂从同一初始策略出发。E两臂使用同一共同规则；实际状态或事件时刻差异逐项报告。R臂也运行事件观察器，保存可释放机会，日历保持初始版本。

**正式预算：8次worker尝试上限。** E-MPC在前两个成功释放事件后，各选择一个连续两轮窗口、每轮两辆车独立求解：2事件×2轮×2车。异常尝试计入额度，release前持久登记；固定线搜索复用同一raw。其余控制拍沿认可实际尾段执行，解析提案与重放另列零调用计数。

每个数值窗口按事件后拍号升序选择：至少两车实际有效运动、各自有本车可行改进方向、两轮零调用源/模型预检通过。首轮来自实际源；第二轮从真实执行后继重新生成。跨事件窗口重叠时跳到首个未被前一数值窗口占用的合法源。若某事件后未出现合格窗口，单列机会不足及具体限制，保留剩余额度，分项交付。

本轮数值目标沿用原J_E，聚焦控制链和协商。全任务时间收益与输入代价收益分别报告。

## 4. 先把在线释放规则写成公式

### 4.1 事件依赖实际状态

为每个资源r定义Clear(i,r,z_i,W_i)：

- 当前实际整车已经位于资源允许释放侧；由矩形支持值/分离面和外向状态区间判断。
- 已认可实际剩余策略、接收反馈及终端保持，在当前资源义务下保持清空或由明确新租约覆盖后续再进入。
- 当前源和后续均满足接收/模式切换/出口守卫；速度、轮角和位姿范围分别核对。
- 当前权限、框架、history、接收链和剩余期限身份有效。

定义最早触发拍为满足Clear及剩余保护余量为正的首个实际拍。明确区分“车身刚离开几何核心”和“完整出口/后续守卫可释放”。后者决定正式事件。保存各子条件首次成立的拍号与最紧面。

A1历史释放点406、B1历史区间、69拍差值作为回归参照；事件代码读取状态和合同，不设车辆专用触发拍号或固定69拍剪切。

### 4.2 从当前合同生成新合同

以当前实际源为起点，固定已经执行的全部命令/history，提案只改未来部分：

1. 当前owner若清空，可把未来未使用的内部占用义务缩短至合法边界。
2. 后继车辆从实际状态使用已认证等待/调轮/运动连接，计算最早可启动源；必要的调轮、制动、接收K保留。
3. 依资源与接收依赖传播后继安排，重新生成实际前缀、接收/后续和占用包络。
4. 所有逐车绝对目标期限非增，至少一辆受影响车提前至少1拍。旧完整合同始终保留为候选。

候选搜索复用既有有限连接族；对整数启动拍按早到晚检查合法范围，最大检查数与来源在执行前登记。保存所有尝试的限制行/资源/接收失败；采用首个满足完整证书的最早合法安排。多个资源同时触发时，按真实请求时刻、资源键、既有破同序规则确定顺序，每拍最多提交一个改框架事务。

释放/传播涉及精确初态的连接，先通过实际接收域和同输入SE2或既有反馈证明接续；每个接缝计算新源、末v/delta、位姿域与守卫。在线“删等待”仅在该等待段及接续被共同规则证明可移除时执行。

### 4.3 期限、归纳与有限协商

采用绝对目标拍d_i与当前拍k；b_i(k)=max(d_i−k,0)，B(k)=max_i b_i(k)。

每个认可改约d_i^new≤d_i^old，至少一个严格下降；每拍执行后，未完成任务的B按时钟推进下降，日历缩短另记调整量。已完成车目标永久保持。

在释放前补齐三条条件命题及推导，保存在release_theory.md：

- **SR-S安全：** 清空守卫、完整前后合同证书、六对组合与同版原子切换给出安全新联合计划。
- **SR-R延续：** 新接收后续含于合法后继集合；执行首拍移位仍给出可行尾段，拒绝时继承旧合同。每次传播接缝逐项列出集合包含。
- **SR-F有限性：** 候选池/协商轮数有限；缺ACK保留旧动作；绝对期限整数非增。给出势函数Phi=sum_i(d_i−d_i_lower)，d_i_lower为模型给出的固定有效下界（可取0作粗界）。每个有效日历改约至少减1，Phi有下界，从而同一有限任务的有效改约次数有界。数值更新按既有每拍执行规则处理。

理论同时说明事务在当前逻辑控制边界内完成的同步假设及失败动作。当前实验运行逻辑采样时钟，实际墙钟另计。

### 任务D：拒绝与后续再触发

从一次真实释放事件实际检查点复制两条零新增求解分支：

1. 缺一个真实受影响端点ACK：旧合同/接收链继续，外部有效独立输入继续；在下一个合法控制边界按固定重试规则重新评估，记录是否恢复释放。
2. 陈旧清空状态或损坏接收/K证书：提案拒绝，执行认可旧首拍并安全续行，后续事件仍按共同规则处理。

固定重试规则：同一actual_history/合同版本/提案内容最多提交一次；源history或相关外框架变化后才重新生成。故障注入只作用于登记的一次尝试，随后恢复正常。两分支执行至目标，零非法提交/输出。

其余零调用fixture覆盖：半开租约与闭占用端点、清空后未来回侵、遗漏永久目标、漏闭包成员、混合outer/inner版本、非法删K/停车调轮、已执行前缀改变、期限上调。保存原始失败与共同规则修复。
